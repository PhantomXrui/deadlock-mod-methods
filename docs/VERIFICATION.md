# 验证：怎样知道只改了该改的部分

验证从“本次允许的差异”出发。允许改骨骼、只允许改 RGB、只允许增加图标，会得到不同的检查边界。不能用同一个规则把所有任务都判定为通过或失败。

## 先保留基线

记录本次输入及当前满意输出的校验值。把新结果写到候选目录，检查通过后才更新当前认可版本。临时构建缓存可以重建，用户唯一的手绘源和当前有效输入必须保留。

## 人物移植检查分层

| 检查层 | 比较什么 | 不能证明什么 |
| --- | --- | --- |
| 编辑输入 | 对象、网格、顶点/面、UV、材质连接、图像、形态键状态、修改器 | 清单一致不代表实际求值后的外观一致 |
| 姿态与空间 | 原骨架和目标骨架的静止姿态、对象矩阵、绑定矩阵、权重映射 | 静止帧正确不保证冲刺或大跳正确 |
| 导出 | 导出前后几何、UV、权重、法线和材质表达 | Blender 材质不一定可被游戏 shader 直接表示 |
| 编译结构 | 骨架、动画、附件、物理/布料块及资源引用 | 结构合法不保证视觉上没有穿模 |
| 实际画面 | 原外貌对照、转头、换弹、冲刺大跳及局部近景 | 只看一种动作不能声称所有动作均通过 |

已有绑定模型走修正导出时，保护范围通常更严格。只改睫毛材质，就应证明其余几何、UV、权重和物理没有被顺手重做。

## 原皮改色检查分层

1. 查材质真正连接的图像，区分 packed 与外部文件；确认用户已经保存的最新手绘内容。
2. 缩图在编译副本进行。保护原图像、UV 与 Alpha/状态遮罩。记录颜色空间、尺寸、格式和 mipmap。
3. 回读编译纹理。区分输入缩放误差和 BC7 等压缩误差；有损结果不能要求 PNG 字节相等。
4. 合并时按 VPK 内部路径比较。若只改四张纹理，其他资源应保持原字节；新增材质或颜色字段须事先写进允许清单。
5. 检查实际加载关系，再到游戏看不同状态和释放方式。不要把另一个同路径覆盖包造成的问题归因到刚改的彩图。

## 用清单限定包内变化

下面是伪代码，用来说明验证关系，不是完整打包器：

```python
before = manifest(approved_package)   # internal_path -> SHA256
after = manifest(candidate_package)
changes = compare_paths_and_hashes(before, after)
assert changes.paths <= allowed_paths
assert expected_additions <= changes.added_paths
assert not changes.unexpected_removals
verify_resource_references(candidate_package)
```

对于保持原结构的任务，还需检查相应模型或编译块；只比较包大小不够。对于刻意修改材质参数的任务，清单应允许这些字段变化，不能要求整个材质字节不变。

## 三种结果分别记录

- **构建验证通过**：输入、编译输出及资源差异符合计划。
- **安装完成**：确认目标位置与加载包，必要的回退点位于游戏加载目录外。
- **游戏检查通过**：列出具体看过的动作、技能状态和局部；未检查的部分写明。

历史版本的游戏反馈不能证明新版本已经安装。图片对比和文件检查也不能替代动态验证。
