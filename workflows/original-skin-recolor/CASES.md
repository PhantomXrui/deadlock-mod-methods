# 原皮改色：构建尝试与排错案例

本页依据“换颜色”工程留下的脚本、检查报告、编译日志、安装收据和历史交流记录整理。公开的是问题解决过程，不是原工程文件、私人聊天或游戏资源。文中的检查结果描述当时那次执行，不保证适用于更新后的游戏文件。

证据分两类：能与本地脚本和产物报告交叉核对的执行记录，以及仅能确认当时讲解内容的历史交互记录。后者不升级成当次重新编译或游戏验收。整体代码组织见 [流水线说明](README.md)，检查口径见 [验证方法](../../docs/VERIFICATION.md)，软件用途见 [工具索引](../../docs/TOOLS.md)。

## 1. 配色像了，原衣服和书本纹样却被压淡

**问题。** 早期配色处理压淡了原有细节。使用者要求直接在现成贴图上改色，保留原花纹。

**实际调整。** 后续代码改为读取原彩图，根据实际三角面 UV 栅格化区域遮罩，在原像素上调整 HSV 和明暗映射。皮肤及明确保留的区域优先保护；保留原 Alpha 和非颜色图。UV 标签只向空白 bleed 延展，不覆盖其他岛。

05 版继续处理靴边碎片误分区：先计算网格连通部件，再按焊接边邻接关系及共享边长度推断细小部件的归属，避免将全部碎三角面都判成金色鞋带。书本纹样、围裙反面边缘和徽章也按实际部位继续精修。

**结果与验证。** 03、05 两次检查记录都确认几何、UV、权重、骨骼指纹不变，原内嵌图保留。历史记录包含真实模型四视图、近景和无光照底色检查；这些是图像精修检查，当时尚非游戏效果验收。

**留下的方法。** “只改色”应在原像素和已知区域上变换，而不是用一个目标 RGB 平涂整片。拓扑变化后重建区域索引，不能盲用旧面编号。

## 2. 用户手绘了新图，只想重建颜色

**问题。** 用户提交了最新保存的 Blender，明确没有改其他部分。若重跑首次配色脚本或重新导出整个人物，会扩大范围，甚至盖掉手绘修改。

**实际处理。** 增加独立图像提取模块。代码沿每个材质的 Base Color 连接定位真实图像，要求唯一且直接的映射；遇到歧义则停止。内嵌图读取当前像素，外部 PNG 使用真实文件；与同颜色空间的基线逐像素比较，仅导出发生变化的图。

脚本断言 Alpha 未改变；若人物工程中的武器图也改变，则停止，避免覆盖独立精修的武器来源。提取前后核对源 `.blend` 哈希，并明确不导出几何。

**结果与验证。** 本次改了上衣、下装、头发三张彩图，新增脸部彩图。原 124 项资源的包变为 125 项；另外 121 个资源保持字节一致，武器、全部技能及模型结构未变。

**状态边界。** 构建校验报告生成于 2026-11-03 20:57，当时尚未安装；后续安装记录见本页末尾，不能将这份较早报告当成永远未安装。

**留下的方法。** 后续重建以最新保存的用户图像为输入。旧配色表是历史方案，不应在每次构建时覆盖新的手绘细节。

## 3. 缩图、Alpha 保护与 BC7 误差需要分开检查

**构建目标。** 控制输出体积，同时保留用户可继续修改的高分辨率原稿。

**实际处理。** 不覆盖编辑源，在独立编译目录中将 4096² 图像按每个 RGBA 通道进行 2×2 box 平均，保存成 2048² 输入。再调用资源编译器生成 BC7 纹理。

**验证过程。** 输入准备报告检查了源哈希、尺寸、通道计算及保存后的量化误差，最大误差约为 0.50002／255。编译日志明确记录成功，独立回读确认 2048²、BC7、10 mip；随后对 RGB 和 Alpha 分别统计压缩误差。

**结论。** “编译前保留 Alpha”不能写成“有损压缩后每个 Alpha 像素都字节相同”。源图与编译输入的计算正确性，和压缩后回读质量，是不同检查。

**证据边界。** 现存记录能够证明这条成功路径，没有证据证明当时先试了某种纹理格式而失败。因此不编造格式试错顺序，也不将 2K／BC7／10 mip 写成所有纹理必须采用的参数。

## 4. 二技能已经调过，正面大画笔仍像原版

**问题。** 用户看到整个二技能与新配色不协调。此前修改过的图片属于 NPR 背光透色，不能代替正面彩图。

**查明原因。** 代码扫描当时 4553 份材质，定位正面画笔、轮廓和地面拖痕的实际纹理归属，再结合当前能力依赖图审查。虽然旧 lantern 模型也引用过画笔材质，相关旧粒子不在当时活动技能的可达图中，不能只凭搜索到旧引用就断言会影响当前大招。

**实际修复。** 为正面、轮廓和拖痕分别制作颜色输入，保持图案与 UV 位置。生成的编辑图恢复到目标 1024²，在编译前逐字节恢复原 Alpha，再编译为 BC7／9 mip。正面材质恢复彩图饱和度和白色乘色，避免新彩图再次被去色或偏色。没有把 `AltTranslucency` 灰阶透明度当成备用彩图涂改。

**结果与验证。** 三张图都有编译前 Alpha 检查和 BC7 回读误差记录。范围验证基于 116 资源的满意包，84 个非二技能资源字节一致，候选包增至 124 资源；人物、武器、普攻和其他技能保持原范围。

**状态边界。** 基础色对照预览不含游戏内全部发光、透明度及粒子叠加。该次修复完成时游戏仍在运行，未当场替换安装，亦未进行当次游戏实测。

**留下的方法。** 一个技能的普通彩图、轮廓、背光、地面拖痕和粒子颜色分别定位。修复“漏色”前先证明漏的是哪一层。

## 5. 普攻、右键和大招漏层，原因在代码遍历范围

**查明的旧实现问题。** 普攻默认修改集合为空，默认配色又跳过普攻，逐字段覆写也为空，所以界面出现了普攻选项，但输出仍保留原色。旧能力列表只遍历四个主技能，漏掉 `AssignAsAltFire` 绑定的右键依赖技能。颜色扫描只处理 `C_OP_SetVec`，还遗漏了 `C_INIT_InitVec` 的 RGB 初始化渐变。

进一步审查发现，只有一维 COLOR_LOOKUP 识别还不够：某些启用的 DIFFUSE 纹理层也使用替代渐变，后续渲染会再乘入颜色。只改初始 RGB 不能覆盖这些层。

**实际修复。** 扩展实际可达资源图、颜色目录和字段类型识别，固定原资源与解码数据哈希。第一阶段增加 32 项；随后增加 20 个 DIFFUSE 色标及 4 个普攻专属材质字段。二技能后续又独立增加 12 项。因此 297、321、333 是不同阶段的目录规模，不能混为同一次结果。

普攻修复只针对已审查的英雄专用覆盖材质，不修改共享模型。它的颜色纹理经检查为全白，因此使用材质 tint 即可改变该层颜色，无需为这个输入再次执行去饱和。

**验证过程。** 测试使用独立覆写配置逐项改色，构建后重新解码，将实际差异与精确修改计划比较；保留 RGBA 第四分量、色标位置、非颜色 DATA 和非 DATA 块。未知资源或其他英雄材质路径在写入前拒绝。实际生产配色也做了逐项回读核对。

**状态边界。** 这些记录证明了覆盖范围和构建输出，不能替代实际右键笔画、三技能连线和大招各阶段的视觉检查。目录中保留中性值的字段不一定发生修改，目录数量大于实际颜色变化数并不矛盾。

## 6. 墨罐残留旧发光色；通用检查为 false 不等于编译失败

**问题。** 修改普通武器彩图与背光后，仍需处理墨罐独立的旧自发光色。

**实际修复。** 精确修改 `g_vSelfIllumTint1`。目标 RGB 使用 `128,80,164`；将目标 RGB 除以其最大通道，再乘原 RGB 最大通道，保留原强度峰值。第四分量、动态亮度表达式、纹理引用及其他材质数据保持原样。

**验证过程。** 补丁后重新解码，建立“原数据仅替换该 tint”的预期结果，与实际完整数据比较。颜色专项检查、非 DATA 块字节一致性和 roundtrip 检查均通过。

通用报告同时出现 `contract_valid=false`。这里的通用契约主要针对粒子；材质修复脚本使用适合本次范围的 `color_only_valid` 和精确数据比较，而不是把一个不适用的总开关当作失败结论。

**留下的方法。** 先确认失败检查适用于当前资源类型。不能删掉所有检查来“让它通过”，也不能因为泛用检查失败就断言资源损坏。此案例没有证据证明发生过编译失败；它记录的是验证契约的适用范围。

## 7. 只改颜色后围裙穿模，实际加载了另一个整模型包

**问题。** 用户报告跑步时围裙比以前更容易穿模，表面上像是改色造成的。

**实际排查。** 检查当前安装包、管理器记录和资源内容，发现额外 VPK 覆盖整个人物模型。对比显示骨骼数量从官方的 233 变成 317；原来的 84 个围裙物理控制项被 28 个次级围裙控制项替换。

**实际修复。** 在游戏关闭后，将额外模型覆盖包移出活动加载目录并保留回退。当前樱染颜色包、其他 VPK、管理器和用户模型贴图保持原样，没有为了这个现象重新自动绑定围裙。

**结果与验证。** 修复收据记录覆盖包已移出、满意包哈希未变、其他包未变、用户素材未改。它验证了安装状态和官方模型／布料加载关系的恢复，不等同于已经完成跑步视觉验收。

**留下的方法。** 纯彩图补丁不会自行重写骨架。出现动作问题时，应先确认实际加载的是哪个模型；给 VPK 改名或换槽位，不能解决包内相同路径的覆盖冲突。

## 8. 图标：编译、目标名称和合并旧包是三件事

**历史问题。** 从空编辑器项目只制作图标，不能自动恢复已有完整 MOD；在素材目录中也找不到已经编译到游戏目录的输出。另一次手动打包只创建了空 VPK，没有实际导入资源树。

**当时给出的解决路线。** 将当前满意包原样导出，单独编译新增图标，再按完整内部路径合并；素材输入位于 `content`，编译输出位于 `game`。打包还要把总资源目录真正加入空包，再保存。

**目标名称问题。** 历史输出名称为 `*_png.vtex_c`，游戏引用的对应人物卡名称则为 `*_psd.vtex_c`。当时指出了这个不匹配并给出目标名调整建议。这里调整的是已经编译完成的资源目标文件名，不能推导成“把 PNG 改后缀就完成编译”。

**证据边界。** 历史答复曾报告三个编译资源内嵌 PNG 与输入一致；本次保存方法没有重新核验那些外部编译产物。目标名修复、重新合并和游戏显示也没有修复后的验证记录。因此本案例只记录诊断与建议，**不宣称图标已经修复并在游戏成功显示**。

**留下的方法。** 源图、编译资源、游戏目标路径和合并后的包分别检查。成功编译一个文件，只能证明其中一环。

## 手绘更新与安装的时间线校正

同一个候选包在不同时间的报告可能出现不同安装状态。已经核对到的记录如下，日期时间均按当时记录的中国标准时间：

| 时间 | 已发生的事 | 能证明什么 | 尚不能证明什么 |
| --- | --- | --- | --- |
| 2026-11-03 20:57 | 手绘彩图更新完成，包与像素验证通过 | 三张彩图变化、增加脸图，其余 121 项资源保持一致；此刻尚未安装 | 新包在游戏中的显示 |
| 2026-11-03 21:41 | 移出额外整模型覆盖包 | 当时活动樱染包未改，其他包与管理器未改，额外模型覆盖已停用 | 围裙跑步表现已验收 |
| 2026-11-03 21:49 | 后续安装收据确认启用了前述同一哈希的手绘更新包 | 候选包已安装，官方模型／布料加载关系恢复，额外覆盖包不存在 | 当次游戏视觉测试通过 |

较早的构建报告写“尚未安装”是准确的阶段快照；后续收据将状态推进为“已安装”。所有这些记录仍明确未做当次游戏目视验收。文档不能拿最早一份快照覆盖后来的执行事实，也不能把安装完成升级成所有动作和特效都已验证。
