# 原皮改色：代码处理与构建流水线

这条路线记录 Codex 如何在已有游戏角色上处理配色、生成最小资源补丁，以及如何证明没有顺带改坏人物或其他技能。它与新人物移植替换分开：只改彩图时继续使用游戏原模型、骨骼、动画和布料，不把整个人物重新导出一遍。

这里公开方法、伪代码和排错经验，不提供模型、游戏贴图、VPK、编译资源、软件或完整工具源码。下文的模块名用于说明历史实现职责，不表示仓库中附有可运行的同名脚本。工具用途与上游入口见 [工具索引](../../docs/TOOLS.md)；检查口径见 [验证方法](../../docs/VERIFICATION.md)；实际问题和修复过程见 [构建排错案例](CASES.md)。

## 1. 输入契约先于构建

开始时固定四类输入：当前用户保存的编辑源、当前满意的成品基线、当前游戏版本的目标资源，以及本次允许修改的范围。不同皮肤工程可以复用代码思路，但不能直接混用人物基础包或另一套已经调好的配色。

| 本次请求 | 允许进入修改集合的内容 | 应继续沿用的内容 |
| --- | --- | --- |
| 人物只改色 | 实际变化的彩图；确有需要且单独审查的纹理引用 | 原模型、UV、骨骼、动画、布料、未改材质 |
| 武器只改色 | 普通／状态彩图、确认生效的武器颜色参数 | 武器形状、UV、原法线、无关遮罩 |
| 一个技能细调 | 该效果实际可达的颜色字段和专用纹理 | 其他技能、人物、武器、时序与运动参数 |
| 加图标 | 目标图标的编译纹理 | 当前包已有的人物、武器和特效 |

先记录输入 SHA-256，再读取和处理；收尾复查源文件没有变化。哈希约束用于发现本次构建期间的意外变动，不把旧哈希当作今后用户不能继续编辑的限制。

## 2. 模块职责

| 历史实现职责 | 输入 | 输出与保护点 |
| --- | --- | --- |
| 分区改色 `recolor_*` | 原彩图、实际网格 UV、区域定义、配色表 | 新彩图；保护皮肤、原 Alpha、原图与几何指纹 |
| 读取手绘 `export_current_colors` | 用户最新保存的 Blender／外部图像、满意彩图基线 | 只导出发生变化的图像；拒绝模糊的材质映射 |
| 准备编译输入 `prepare_compile_inputs` | 已导出的编辑源及其哈希 | 独立缩图副本和通道检查记录；不覆盖编辑源 |
| 纹理构建 `rebuild_textures` | 编译输入、已核实的资源编译器配置 | 真正的 `.vtex_c`、日志、尺寸／格式／mipmap 收据 |
| 特效目录与计划生成 `detail_support`、`build_effects` | 当前技能依赖、原资源、基础色、逐字段覆写 | 明确资源路径与字段位置的颜色修改计划 |
| 材质／粒子补丁工具 | 原资源哈希、受限路径、原值与新值 | 编译资源补丁；拒绝未知路径和不匹配的原值 |
| 独立验证 `verify_*` | 基线、候选包、修改计划、构建收据 | 包内差异、通道误差和范围证明；不负责安装 |
| 安装记录 | 已验证候选包、当前安装清单 | 实际安装位置、内容哈希和回退记录；不自动等同游戏验收 |

把这些职责分开，是为了让“本次只更新手绘颜色”跳过重新配色、重新绑骨和重新生成技能等无关步骤。

## 3. 首次配色：原像素上的分区变换

早期处理曾把原纹样压淡。后续实现改为读取原彩图，而不是用平涂块重新制作全部纹理。

代码先建立区域标签，再将实际三角面的 UV 栅格化为像素遮罩。区域内采用色相调整、饱和度控制和保留明暗关系的映射；皮肤及指定保留区优先。这样可以保留书本纹样、布纹和墨迹，而不是要求每个像素都等于目标 RGB。

```python
# 说明性伪代码；需要按自己的资源、颜色空间和图像库实现
original = read_image(source_image)
labels = rasterize_uv_triangles(mesh_uv, face_regions)
labels = extend_labels_into_empty_bleed(labels, padding)
result = original.copy()

for region in editable_regions:
    mask = labels == region.id
    result.rgb[mask] = recolor_preserving_shading(
        original.rgb[mask], region.target_color
    )

result[protected_pixels] = original[protected_pixels]
result.alpha = original.alpha
assert geometry_uv_weights_bones_fingerprint() == before_fingerprint
```

颜色延展只能进入 UV 岛外空白，不能压过其他岛。区域索引依赖实际拓扑；换了网格就不能复用旧面编号。

对靴边细小碎片，历史实现使用连通部件和焊接边邻接关系，通过共享边长度确定更可信的相邻部位，避免把所有细碎三角面都归成金色鞋带。这是针对真实分区错误的修复，不是通用的“越小越应该合并”规则。

参考配色可以单独记录，例如粉色 `230,142,183 / #E68EB7`、天蓝 `121,185,223 / #79B9DF`、浅衣 `231,223,238 / #E7DFEE`、深紫 `118,81,168 / #7651A8` 和暖金 `208,173,112 / #D0AD70`。这些值表示色彩方向，实际像素仍保留深浅变化。

## 4. 用户已经手绘：读取当前图像，不重跑旧方案

后来用户在 Blender 中画了新颜色，正确输入变成最新保存的图像。再次运行旧配色脚本会抹掉后续涂画，因此增加了独立的“读取当前彩图”路径。

历史脚本从材质的实际 Base Color 连接确定图像，要求唯一且直接的图像映射。混合或程序材质不静默猜第一张图，而是停止并要求实现者审查对应关系。它还区分内嵌图和外部 PNG；未内嵌的外部图按真实磁盘来源复制。

```python
source_hash = sha256(saved_blend)
changed_images = []

for material in reviewed_material_mapping:
    current = resolve_unambiguous_base_color_image(material)
    baseline = load_baseline_in_same_color_space(material)
    assert current.size == baseline.size

    if pixels_equal(current, baseline):
        continue
    assert alpha_equal(current, baseline)
    assert not conflicts_with_independent_weapon_source(material)
    changed_images.append(export_current_pixels(current))

assert sha256(saved_blend) == source_hash
assert no_geometry_was_exported()
```

这段算法的重点是“从实际保存的当前像素出发”和“拒绝越界变化”。它不保证能自动识别所有着色节点组合，也不把保存 `.blend` 视为所有外部图片都已经保存。

## 5. 编译输入与资源输出分层验证

保留高分辨率编辑源，在单独目录创建编译输入。一次实际更新使用 4096² 图像，按每个 RGBA 通道做 2×2 box 平均，生成 2048² 输入，再编译为 BC7／10 mip。这是该案例的参数，不是所有项目的固定要求。

检查分为两个层次：

1. **准备阶段**：源图哈希不变，缩图尺寸正确，RGBA 计算与预期一致，量化误差在明确阈值内。
2. **压缩阶段**：独立回读 `.vtex_c`，确认格式、尺寸、mipmap，统计 RGB 与 Alpha 的压缩误差。

Alpha 可能是状态或显露遮罩，不能因看起来像透明度就清空。编译前逐字节保留原 Alpha，与有损 BC7 回读后逐像素完全一致，是两个不同命题。记录应说明保护发生在哪一层。

PNG 改扩展名不能变成 `.vtex_c`。编译产物还必须对应游戏实际引用的内部路径，不能把本机输出目录当作 VPK 内部根目录。

## 6. 武器和技能：建立可审查的修改计划

先从当前英雄及能力绑定追踪实际资源图，包括右键依赖技能、子粒子、材质、纹理和继承关系。只按 `glow`、`trail` 等名称搜索不能证明某个字段控制目标画面。

计划至少记录以下内容：

```text
资源内部路径
原资源 SHA-256 与解码数据指纹
字段路径、字段类型、原值
新 RGB 与保留的第四分量
所属技能／画面层，以及该层为何实际生效
```

基础配色提供共同风格，逐字段覆写处理某个阶段的特殊颜色。案例里的本地细调器只是编辑这些数据的辅助界面，本仓库不附该程序；真正需要保存的是数据层次、修改计划和构建逻辑。

实现时分别识别：

- `C_OP_SetVec` 和 `C_INIT_InitVec` 的 RGB／渐变输入。
- 实际启用的 SpriteCard 颜色查找与 DIFFUSE 渐变，而不只识别一种纹理类型。
- 父粒子和控制点供色，避免给继承层虚构独立 RGB。
- 材质 tint、自发光、普通彩图与 NPR 背光透色的区别。
- 普通武器彩图、特殊状态彩图和状态 Alpha 的区别。

仅改色时保留渐变位置、时序、速度、数量、控制点、子资源、碰撞与伤害相关数据。写入前检查实际表示空间：RGB 0–255、浮点 0–1、线性／sRGB 及大于 1 的发光强度不能混为一谈。

一项实际武器修复只改变 `g_vSelfIllumTint1` 的 RGB 方向，保持原 RGB 峰值、第四分量和动态亮度。它采用“目标 RGB 除以目标最大通道，再乘原峰值”，并不是直接把所有发光值加满。目标全黑需要单独处理；这种峰值保留也不代表感知亮度完全不变。

## 7. 构建最小补丁，再比较候选包

人物颜色更新时，以满意包为基线，合入本次实际变化的纹理。验证器要求候选包的变化集合与导出图像集合精确对应，而不只检查“生成了一个能打开的 VPK”。

```python
removed = baseline.paths - candidate.paths
added = candidate.paths - baseline.paths
changed = {
    p for p in baseline.paths & candidate.paths
    if baseline.bytes(p) != candidate.bytes(p)
}

assert not removed
assert added | changed == approved_changed_resources
for path in baseline.paths - approved_changed_resources:
    assert candidate.bytes(path) == baseline.bytes(path)
```

纯彩图验证还拒绝意外新增或修改模型、网格、材质、粒子和数据资源。技能改色则采用相应范围的白名单及类型检查，不能沿用人物纹理专用规则阻止本次确实允许修改的材质。

某次旧基础包同时携带人物纹理和旧特效，仅叠加新输出会留下未管理的旧粒子。后续改为纯人物纹理基底，加上由当前配置完整生成的特效。之后的手绘更新又以独立纹理覆盖层维护；不要把已合成成品随意塞回基础包造成层级混乱。

## 8. 收据说明验证边界

可重建记录应把源图、编辑源、编译输入、脚本版本、目标资源、候选包和验证结果关联起来。后续改技能时沿用最新人物颜色，后续改人物时保留满意武器与技能。

构建验证、安装和游戏观察分别记账。一个构建报告在生成时写“尚未安装”，后来可能存在同一哈希的安装收据；判断状态应沿时间线核对，而不是只读取最早一份报告。安装成功也不代表已经验证了右键画图、目标连线、特殊状态和跑跳中的表现。

这套设计的结果是把大任务拆成可审查的改动集合：找到实际输入，限制修改范围，独立回读输出，再在游戏中验证计划内的画面。具体尝试、失败原因和证据边界见 [案例记录](CASES.md)。
